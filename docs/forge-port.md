# Forge 1.20.1 port verification

The reference is NuclearCraft: Overhauled 2o.9.7 at `ef28c65`. The port builds with Java 17, Mojang mappings, and Forge 47.4.10. The current installed Auram snapshot runs Forge 47.4.18. The Forge code currently comes from the legacy NuclearCraft source and uses no Neohaul implementation code.

### Default processor recipes

The world's `nuclearcraft-processors.toml` accepts the legacy `default_processor_recipes_global` switch and `default_processor_recipes` array. Both default to true. The 20 array positions match `processor_time`. Turning off the global switch removes all shipped processor recipes. Turning off one array entry removes that machine’s shipped recipes. Both switches include recipes discovered from material tags by the Melter and Pressurizer. The Electric Furnace still uses vanilla and modded furnace recipes, as it did in 2o.9.7.

Datapacks and KubeJS keep their own recipes, including replacements that reuse a stock recipe ID. Omit `nuclearcraft_default` when copying a packaged recipe JSON for independent use. The server applies the switches when the world starts and filters the recipe catalog again when datapacks reload. JEI receives the enabled recipes. Setting `ore_processing` to false also disables generated Melter ore recipes and the Manufactory’s shipped ore and raw ore recipes. The Manufactory can still grind ingots.

### Melter material recipes

The Melter now melts ore, tiny dust, nuggets, and storage blocks where the material is available. An ingot or dust gives 144 mB, a metal ore gives 288 mB, a nugget gives 16 mB, and a metal storage block gives 1,296 mB. Gems and their dusts give 666 mB, gem ores give 1,332 mB, and gem nuggets give 74 mB. The recipe duration of a nugget is 800/9 ticks. Progress carries forward between batches, so nine metal nuggets use exactly the time and power of an ingot. Sulfur dust restores the legacy 666 mB yield. Existing tank contents retain their saved amounts.

Discovery uses shared `forge` and `c` item tags and a source fluid from `molten_<material>` in either namespace. Existing NuclearCraft materials use their registered fluid. ### Processor fluid controls

Click a tank to configure its faces. An input can accept fluid, expose it for extraction, auto-eject it, or disconnect. The Melter now uses the same output controls as the other processors. Its product tank exposes fluid for extraction, auto-ejects it to a neighboring Forge fluid handler, or disconnects on each selected face. Auto-eject retains fluid that the destination cannot accept. Alt-click a face to restore the selected tank’s defaults. Ctrl-click, or Command-click on macOS, disables all its faces. Shift-clicking the tank empties it.

Use **Mode** on a product tank to choose hold, void excess, or void. Hold waits for the full output volume to fit. Void excess discards only surplus of the matching fluid. Void clears the tank and discards future products. An input tank can keep its leftovers or discard them when a completed batch leaves the machine unable to start another. Each setting applies to the selected tank. Machines with two inputs default to **Split**, which keeps matching fluid in one accessible tank per face. **Share** permits the same fluid in both tanks when the input rules allow it.

Existing Forge saves retain their fluid amounts and face settings. The Melter stores its fluid under `output` and its new controls under `fluid_sides` and `fluid_output_mode`. Imported bidirectional and auto-input modes use the same face order, encoded as six base-six digits plus 4096 with bidirectional 4 and auto-input 5. ### Per-slot processor item automation

In a processor menu, choose **Slots**, select an ingredient, product, or upgrade slot, and click a face button to change that slot’s mode. ### Processor upgrades

### Quantum Computer

Connect exactly one controller, qubits, gates, and other parts face to face. The shape is unrestricted. Connections use loaded block entities and pause an existing circuit while any of its chunks unload. A redstone rising edge queues one operation. Controllers reset the state, gates apply the configured operation, and qubits measure and update comparators to 0 or 15. The 26 gates include the single-qubit operators, their controlled forms, Swap, and Controlled Swap. The original models and gate textures ship in the JAR. Qubit cores cycle through colors and flash red for zero or blue for one.

Sneak-use the Multitool on a gate to start editing its next setting. When selecting qubits, use the tool on connected qubits, then use it on the gate to save the selection. Controls and targets use distinct qubit IDs. The two Swap lists pair their entries in selection order. For an angle, face the desired heading and use the tool in the air before saving. The original angle precision defaults to 16 steps per turn. Use an OpenQASM or Qiskit generator with the Multitool to start recording redstone operations, then use it again to write the circuit under `nc_quantum` in the world directory. OpenQASM exports use the standard OpenQASM 2 gate library. Qiskit exports are Jupyter notebooks and construct the circuit locally.

Move `register_quantum` to `config/nuclearcraft-quantum-availability.toml`. It controls the built-in recipes, creative listing, and circuit activation. Registry IDs stay present for existing saves and scripts. Move `quantum_dedicated_server`, `quantum_max_qubits`, and `quantum_angle_precision` to `world/serverconfig/nuclearcraft-quantum.toml`. The default limit is 16 qubits and dedicated servers need to opt in. The simulator doubles its state size for every added qubit. The configuration supports up to 28 qubits when the server has enough heap for them.

Circuits whose vectors exceed 8 MiB store the amplitudes in compressed `.qstate` files under `world/data/nuclearcraft_quantum`. Back up that directory with the world. The controller retains its file reference in chunk NBT, and a state update atomically replaces the file after writing it. A failed write keeps the last saved vector and retries while the controller is loaded. If a file is missing or corrupt, restore it from a world backup before pulsing the circuit again. A controller reset deliberately clears an unreadable state. Legacy inline vectors still load. ### Feral and glowing ghouls

The legacy entity IDs are `nuclearcraft:feral_ghoul` and `nuclearcraft:glowing_ghoul`. Their modern spawn eggs use the matching `_spawn_egg` IDs. The Nuclear Wasteland biome spawns feral ghouls in daylight and glowing ghouls underground where the chunk radiation exceeds the legacy background threshold. Both use the original model, adult proportions, wall climbing, husk loot, and charge and death sounds. Feral ghouls can leap at nearby targets. Glowing ghouls use the original emissive layer. The dimension plays its nine original ambient tracks on the music channel.

Feral and glowing attacks add 0.33 and 3.8 Rad respectively at the base difficulty multiplier. Successful attacks on nonhostile living targets inflict poison and add radiation to the victim's buffered exposure. The amount increases with local difficulty and absorbs over `radiation_poison_time`. The two legacy attack settings retain their names in `world/serverconfig/nuclearcraft-radiation.toml`. Ghouls retain radiation buffs at a fatal dose. Villagers and other NPCs can convert to feral ghouls at a fatal dose or on entering the Wasteland. Conversion preserves their name, AI setting, and persistence and uses Forge's conversion and spawn events.

Move the two `register_entity` booleans to `world/serverconfig/nuclearcraft-entities.toml`, in feral then glowing order. Registered entity IDs remain available to saves and datapacks. A disabled type cannot spawn naturally and discards any loaded instances. The legacy 64-block default tracking range maps to four Forge tracking chunks.

### Radiation Scrubber

The block, item, recipe type, and menu use `nuclearcraft:radiation_scrubber`. It reserves the inputs for a batch and keeps them, along with partial progress, when the chunk unloads or the server stops. With output set to Hold, a full output tank or slot stops energy use and radiation removal. The redstone control in the menu enables pausing when powered. Sneak-use the block with an empty hand to read its measured removal rate and effective efficiency.

| Medium | Consumed | Produced | Ticks | FE/t | Efficiency |
| --- | --- | --- | ---: | ---: | ---: |
| Borax | 1 borax | 1 irradiated borax | 12,000 | 200 | 100% |
| RadAway | 250 mB RadAway | 250 mB ethanol | 2,400 | 40 | 500% |
| Slow RadAway | 250 mB Slow RadAway | 250 mB redstone ethanol | 96,000 | 20 | 25% |

The `radiation_scrubber_time`, `radiation_scrubber_power`, and `radiation_scrubber_efficiency` arrays map to `ticks`, `energy_per_tick`, and `efficiency` under `scrubber.borax`, `scrubber.radaway`, and `scrubber.slow_radaway` in `world/serverconfig/nuclearcraft-radiation.toml`. The nonlinear curve's four values map in order to `scrubber.curve_base`, `scrubber.curve_divisor`, `scrubber.curve_scale`, and `scrubber.curve_root`. The radius, linear fraction, and nonlinear switch keep their original names. Nearby full collision blocks, including glass, reduce efficiency using the legacy distance and overlap weights. The old environment registry tracked only one position per Scrubber, so the port measures the loaded area directly.

A datapack or KubeJS recipe can choose a stock `medium` or supply its own `ticks`, `energy_per_tick`, and `efficiency`. Supply at least one of `item_input` and `fluid_input` and at least one of `item_output` and `fluid_output`. These use a counted Forge ingredient, a fluid ID or tag and amount, an item stack, and a fluid stack respectively. Converted Scrubber saves need to map input and output inventories, both tanks, the reserved media, recipe ID, and progress into the Forge block entity. The `redstoneControl` flag retains its key.

### Processor radiation

The Decay Hastener's 87 recipes use their legacy process radiation rates. Crystallizing irradiated borax solution emits 8.25 mRad/t. Only a tick that advances the recipe contributes process radiation. A machine that has stopped due to redstone, lack of power, or a blocked output contributes zero. Processing resumes from the existing saved recipe and progress, and each tick recalculates the emission. The chunk sampler still honors `radiation_tile_entities` and container shielding.

Single-block processor recipes, including Melter and fluid processor recipes, accept an optional nonnegative `radiation` value in Rad/t. Recipes without the field default to zero. Datapacks and KubeJS can supply the value in the recipe JSON. JEI shows nonzero rates on the recipe arrow. Legacy scripts can move the third processor extra into this field.
